## Краткое описание

Система автоматического анализа тональности комментариев для социальной сети с ежедневным объёмом до **500 000 комментариев**. Решает задачу мониторинга контента для соответствия требованиям РКН, снижения операционных расходов на модерацию и повышения качества пользовательского опыта.

**Ключевые показатели системы:**
- Охват: **100 %** входящего потока (vs. ~2 % при ручной модерации)
- Время реакции: **≤ 30 сек** (vs. нескольких часов)
- Recall по токсичным комментариям: **≥ 0.95**
- Снижение нагрузки на модераторов: **−85 %**

## 1. Цели и предпосылки

### 1.1. Зачем идём в разработку продукта?

**Бизнес-цель.** Автоматизировать мониторинг пользовательских реакций на контент (посты, рекламу, новости) в социальной сети, чтобы:
- оперативно выявлять токсичный и запрещённый контент и снижать риск санкций со стороны Роскомнадзора (РКН);
- сокращать операционные расходы на ручную модерацию;
- повышать качество пользовательского опыта за счёт быстрого удаления вредоносного контента.

**Почему ML лучше текущего подхода?** Сейчас анализ тональности проводится вручную: модераторы читают выборочные комментарии или анализ не проводится вовсе. Поток составляет до 500 000 комментариев в сутки. При таком объёме ручная проверка охватывает менее 1–2 % контента, что делает процесс медленным, дорогостоящим и субъективным.

Система на базе ML позволит:
- обрабатывать 100 % поступающих комментариев в режиме реального времени;
- автоматически блокировать явно нарушающий правила контент (recall по токсичным комментариям ≥ 0.95);
- направлять на ручную проверку только пограничные случаи (≈ 10–15 % потока), снижая нагрузку на модераторов в 6–10 раз;
- вести аналитику тональности аудитории для улучшения редакционной политики.

**Критерии успеха итерации (бизнес).** Итерация считается успешной, если:
- доля токсичных комментариев, прошедших «незамеченными», снизилась на 80 % по сравнению с текущим уровнем;
- среднее время реакции на токсичный комментарий сократилось с нескольких часов до ≤ 30 секунд;
- не зафиксировано ни одного штрафа со стороны РКН по контенту, прошедшему через систему.

### 1.2. Бизнес-требования и ограничения

**Функциональные требования (ФТ)** — что система *должна делать*:

1. Принимать входящий поток комментариев в режиме реального времени и классифицировать каждый по четырём классам: `positive`, `neutral`, `negative`, `toxic`.
2. Автоматически скрывать комментарии с высокой вероятностью токсичности (score ≥ 0.92) без участия модератора.
3. Помещать пограничные комментарии (0.70 ≤ score < 0.92) в очередь ручной проверки с указанием оценки модели.
4. Предоставлять модераторам интерфейс (Admin Dashboard) для просмотра очереди, вынесения решений и просмотра истории.
5. Сохранять все предсказания модели (label, scores, model_version, timestamp) для аудита по требованию регулятора.
6. Предоставлять дашборд с агрегированной статистикой тональности аудитории в разрезе контента и времени.
7. Поддерживать механизм апелляции: пользователь может оспорить автоматическую блокировку.
8. Уведомлять модераторов о новых элементах в очереди в режиме реального времени (WebSocket push).

**Нефункциональные требования (НФТ)** — как система *должна работать*:

| Категория | Требование |
|---|---|
| **Производительность** | Latency инференса p99 ≤ 300 мс; throughput ≥ 50 RPS номинально, ≥ 150 RPS в пике |
| **Надёжность** | Uptime ≥ 99.9 % (< 9 ч простоя в год); graceful degradation при отказе Kafka |
| **Восстановление** | RTO ≤ 15 мин, RPO ≤ 5 мин (Kafka offset) |
| **Точность** | Recall по `toxic` ≥ 0.95; Precision по `toxic` ≥ 0.90; FP-rate ≤ 2 % от всего потока |
| **Масштабируемость** | Горизонтальное масштабирование инференс-сервиса через K8s HPA без изменения кода |
| **Локализация данных** | Все данные хранятся на серверах в РФ (149-ФЗ, 152-ФЗ) |
| **Безопасность** | Шифрование трафика TLS; аутентификация модераторов через SSO (OAuth2/OIDC); аудит-лог неизменяем |
| **Наблюдаемость** | Метрики (Prometheus), дашборды (Grafana), алерты при деградации качества модели (PSI > порога) |
| **Стоимость** | Бюджет инфраструктуры MVP ≤ 150 000 руб./мес. |

**Описание бизнес-процесса пилота.** Пилот проводится на 10 % реального трафика (≈ 50 000 комментариев/сутки) одной из тематических лент. Система работает в режиме «shadow mode»: автоматически блокирует только явно токсичные (score ≥ 0.90), остальные скрывает в очередь ручной проверки параллельно с текущим процессом модерации. Это позволяет сопоставить решения системы с решениями модераторов без ущерба для пользователей.

**Критерии успешного пилота:**
- Precision по классу «токсичный» ≥ 0.90 (не более 10 % ложных блокировок);
- Recall по классу «токсичный» ≥ 0.95 (не более 5 % пропущенных нарушений);
- Время обработки одного комментария p99 ≤ 300 мс;
- Снижение объёма ручной проверки модераторами ≥ 60 %.

### 1.3. Скоуп проекта и итерации

**В скоуп MVP входит:**
- Модель классификации тональности комментариев (4 класса).
- Стриминговый пайплайн обработки на базе Apache Kafka.
- API-сервис инференса (FastAPI + ONNX Runtime).
- Хранение предсказаний и история версий моделей (MLflow + PostgreSQL).
- Базовый дашборд модерации (Grafana).
- Интеграция с существующим API социальной сети (webhooks).

**Не входит в MVP (технический долг):**
- Персонализированный анализ тональности по пользователям (профилирование авторов).
- Многоязычная поддержка (пилот — только русский язык).
- Автоматическое дообучение модели в продакшне (MLOps-пайплайн обновления).
- Аналитика для редакционного отдела (расширенный BI-дашборд).
- Обнаружение координированных атак и ботов.

**Качество кода и воспроизводимость:**
- Все эксперименты логируются в MLflow.
- Инференс-сервис покрыт юнит-тестами (coverage ≥ 80 %).
- Конфигурация инфраструктуры описана в Terraform + Docker Compose.

### 1.4. Предпосылки решения

- **Данные:** архивные комментарии социальной сети за последние 6–12 месяцев с разметкой (частичная разметка модераторами, дополненная краудсорсингом).
- **Язык:** русскоязычный контент как основной; возможно наличие транслита и ненормативной лексики.
- **Гранулярность:** классификация на уровне отдельного комментария.
- **Горизонт инференса:** онлайн (real-time), обновление модели не чаще 1 раза в 2 недели.
- **Предположение о дрейфе данных:** возможен сезонный и новостной дрейф; требуется мониторинг распределения входных данных.

## 2. Методология

### 2.1. Постановка задачи

С технической точки зрения задача решается как **многоклассовая текстовая классификация** (multi-class text classification):

- **Вход:** текст комментария (строка, до 2000 символов).
- **Выход:** одна из четырёх меток: `positive`, `neutral`, `negative`, `toxic` + вероятностный вектор.
- **Подзадача:** бинарная классификация `toxic` / `non-toxic` используется как основной фильтр для автоматических действий.

Решение строится на предобученных языковых моделях (трансформер-архитектура): дообучение ruBERT / DeepPavlov BERT ru на размеченных данных социальной сети.

**Бейзлайн:** словарный классификатор (TF-IDF + Logistic Regression) на том же наборе данных — быстро обучается, интерпретируем, служит нижней границей качества.

### 2.2. Блок-схема решения

Схема пайплайна (бейзлайн и MVP совпадают по верхнему уровню, различаются на этапе обучения):

```
[Сырые данные] → [Предобработка текста] → [Векторизация]
                                                ↓
         [Baseline: TF-IDF + LogReg]   [MVP: fine-tuned ruBERT]
                                                ↓
                         [Валидация на hold-out]
                                                ↓
                         [MLflow: логирование метрик и артефактов]
                                                ↓
                         [ONNX-экспорт модели]
                                                ↓
                         [Деплой в инференс-сервис (FastAPI)]
                                                ↓
                 [Kafka-consumer → инференс → запись в PostgreSQL]
```

Детальная диаграмма бизнес-процессов — см.: [AS-IS](diagrams/bpmn_as_is.md) · [TO-BE](diagrams/bpmn_to_be.md)

### 2.3. Этапы решения задачи

#### Этап 1 — Подготовка данных

**Источники данных:**

| Данные | Источник | Ответственный | Качество |
|---|---|---|:---:|
| Архивные комментарии с метками модераторов | БД социальной сети | DE | Частично |
| Открытые датасеты по русскоязычной токсичности (RuToxic, OK-ML) | Публичные репозитории | DS | ✓ |
| Краудсорсинговая разметка (Toloka) | Яндекс.Толока | DE/DS | Планируется |
| Словарь запрещённой лексики | Юридический отдел + открытые источники | PO | ✓ |

**Целевая переменная:**

| Метка | Описание |
|---|---|
| `positive` | Позитивная реакция, поддержка, благодарность |
| `neutral` | Нейтральный комментарий без явной эмоциональной окраски |
| `negative` | Негатив, критика, недовольство (не нарушающий правила) |
| `toxic` | Токсичный контент: оскорбления, угрозы, запрещённые высказывания |

**Объём выборки для MVP:** не менее 500 000 размеченных примеров, из них 15–20 % — класс `toxic` (балансировка через over-sampling/class weights).

**Разбиение:** train/val/test = 70/15/15 по стратифицированному сэмплингу; тестовая выборка изолирована с момента начала проекта.

**Предобработка:**
- Нормализация регистра, удаление дублирующихся пробелов.
- Обработка эмодзи (транслитерация или замена на семантический токен).
- Исключение спам-дублей (косинусное сходство > 0.95 → дедупликация).
- Маскировка персональных данных (имена, телефоны, email).

#### Этап 2 — Бейзлайн (TF-IDF + Logistic Regression)

**Входные данные:** очищенный текст комментариев.

**Техника:**
- `TfidfVectorizer`: уни- и биграммы, max_features = 200 000, sublinear_tf = True.
- `LogisticRegression`: C = 1.0, class_weight = 'balanced', solver = 'lbfgs'.

**Метрики-цели для бейзлайна:**

| Метрика | Класс | Цель |
|---|---|---|
| Macro F1 | все классы | ≥ 0.75 |
| Recall | `toxic` | ≥ 0.88 |
| Precision | `toxic` | ≥ 0.85 |
| Inference latency | — | ≤ 5 мс/запрос |

#### Этап 3 — Основная модель (fine-tuned ruBERT)

**Модель:** `DeepPavlov/rubert-base-cased` (или `ai-forever/ruBerta-large`), дообученная на задачу классификации.

**Техника обучения:**
- Tokenizer: WordPiece, max_length = 256 токенов (95-й перцентиль длин).
- Batch size = 32, learning rate = 2e-5, linear warmup (10 % шагов), 5 эпох.
- Аугментация: back-translation (ru→en→ru), случайная перестановка предложений.
- Early stopping по val F1 (patience = 2).
- Hardware: 1× GPU A100 (или 2× V100) ≈ 6–8 часов обучения.

**Метрики-цели для MVP:**

| Метрика | Класс | Цель |
|---|---|---|
| Macro F1 | все классы | ≥ 0.88 |
| Recall | `toxic` | ≥ 0.95 |
| Precision | `toxic` | ≥ 0.90 |
| Inference latency (ONNX) | — | ≤ 50 мс/запрос |
| Throughput | — | ≥ 200 запросов/с |

**Связь с бизнес-метриками:**
- Recall по `toxic` ≥ 0.95 → не более 5 % нарушений пройдут «незамеченными» → минимизация штрафов РКН.
- Precision по `toxic` ≥ 0.90 → не более 10 % ложных блокировок → снижение негатива у пользователей.

**Риски моделирования:**

| Риск | Митигация |
|---|---|
| Дисбаланс классов (toxic < 5 % трафика) | Стратифицированная выборка + focal loss |
| Дрейф данных (новая лексика, мемы, сленг) | Мониторинг KL-дивергенции + ежемесячная доразметка |
| Эвазионные атаки (транслит, замена букв) | Нормализатор unicode + символьные n-граммы как признаки |

#### Этап 4 — ONNX-экспорт и оптимизация

- Конвертация модели в ONNX-граф с dynamic axes для переменной длины входа.
- Квантизация: INT8 post-training quantization (потеря качества < 1 % F1).
- Профилирование throughput на target-железе (CPU: 16 vCPU, optional GPU T4).
- Результат: ONNX-файл + токенизатор, зарегистрированные в MLflow Model Registry.

#### Этап 5 — Интеграция с продакшн-пайплайном

- Kafka consumer читает топик `comments.raw`, вызывает инференс-сервис.
- Результат (`label` + `scores` + `model_version`) записывается в PostgreSQL и в топик `comments.scored`.
- Moderation Service подписывается на `comments.scored`, применяет пороговые правила.

## 3. Подготовка пилота

### 3.1. Способ оценки пилота

Пилот проводится методом **shadow mode** в течение 4 недель на 10 % трафика одной тематической ленты (≈ 50 000 комментариев/сутки). Система работает параллельно с текущим процессом ручной модерации:

1. Модераторы выносят решения независимо от системы (как обычно).
2. Система одновременно классифицирует те же комментарии.
3. Раз в 3 дня проводится сравнение: решения системы vs. решения модераторов.

Это позволяет оценить качество без риска для пользователей и собрать ground truth.

### 3.2. Что считаем успешным пилотом

| Метрика | Порог | Обоснование |
|---|---|---|
| Recall по toxic | ≥ 0.95 | Не более 5 % пропущенных нарушений — требование регулятора |
| Precision по toxic | ≥ 0.90 | Не более 10 % ложных блокировок — UX-требование |
| Latency p99 (end-to-end) | ≤ 300 мс | Пользователь не должен замечать задержки |
| Снижение очереди ручной проверки | ≥ 60 % | Снижение операционных расходов |
| Uptime системы | ≥ 99.5 % | SLA пилота |

### 3.3. Подготовка пилота

**Вычислительные ресурсы пилота:**
- Инференс-сервис: 2 инстанса FastAPI + ONNX Runtime на CPU (8 vCPU, 16 GB RAM каждый).
- Kafka: 3-нодовый кластер (существующая инфраструктура).
- PostgreSQL: отдельная БД на 500 GB SSD.
- Ожидаемая стоимость: ≈ 35 000 руб./мес. (облачные ресурсы YC/Selectel).

**Логирование пилота:**
- Все предсказания сохраняются с timestamp, model_version, scores.
- Мониторинг дрейфа: дневное распределение классов сравнивается с обучающей выборкой (PSI).
- Алерты (Grafana): при recall по toxic < 0.93 или latency p99 > 400 мс.

**Риски пилота:**
- Отказ Kafka → fallback: комментарии ставятся в очередь ручной проверки (graceful degradation).
- Подозрение на эвазионные атаки → активация символьного нормализатора.

## 4. Внедрение для продакшн-системы

### 4.1. Архитектура решения

Система строится на микросервисной архитектуре с асинхронной обработкой через Apache Kafka. Детальная схема — см. [architecture.md](diagrams/architecture.md).

**Компоненты и их назначение:**

| Компонент | Назначение | Технология |
|---|---|---|
| Comment Ingestion Service | Приём комментариев от фронтенда, запись в Kafka | Go + Kafka Producer |
| Kafka Cluster | Шина событий; топики: `comments.raw`, `comments.scored` | Apache Kafka 3.x |
| Sentiment Inference Service | Инференс модели; потребляет из `comments.raw`, пишет в `comments.scored` | FastAPI + ONNX Runtime |
| Moderation Service | Применяет бизнес-правила (пороги), управляет статусом комментариев | Python + FastAPI |
| Feature Store / PostgreSQL | Хранение предсказаний, истории модерации, пользовательских профилей | PostgreSQL 15 + TimescaleDB |
| Redis Cache | Кэш результатов инференса (дедупликация повторных текстов) | Redis 7 |
| MLflow Registry | Версионирование и управление жизненным циклом моделей | MLflow + S3-совместимое хранилище |
| Model Training Pipeline | Переобучение модели по расписанию или при дрейфе | Airflow + PyTorch |
| Monitoring Stack | Мониторинг метрик системы и качества модели | Prometheus + Grafana |
| Admin Dashboard | Интерфейс модераторов: очередь, статистика, апелляции | React + REST API |

**Распределённый характер хранения данных:**

Данные хранятся в нескольких местах — разные требования к скорости доступа, объёму и стоимости:
- **Kafka** — горячие события (TTL 24 ч), буферизация при пиковой нагрузке.
- **Redis** — кэш предсказаний (TTL 1 ч), снижает нагрузку на инференс при повторяющихся текстах.
- **PostgreSQL** — «холодное» хранилище предсказаний и истории модерации, индексируется по времени.
- **Object Storage (S3)** — артефакты моделей (ONNX-файлы, веса), обучающие датасеты.

### 4.2. Описание инфраструктуры и масштабируемости

**Выбранная инфраструктура:** облачная платформа (Yandex Cloud или Selectel) — соответствие российскому законодательству о локализации данных.

| Компонент | Конфигурация MVP | Scale-out |
|---|---|---|
| Inference Service | 2× 8 vCPU, 16 GB (CPU-инференс) | K8s HPA; опционально GPU T4 |
| Kafka | 3 брокера, 6 партиций, replication factor = 3 | Добавление брокеров, увеличение партиций |
| PostgreSQL | Primary + 1 Read Replica, 500 GB SSD | Партиционирование по дате, read replicas |
| Redis | 1 мастер + 1 реплика, 8 GB RAM | Redis Cluster при нагрузке > 10k RPS |

**Плюсы:**
- Kafka обеспечивает устойчивость к пикам (буферизация до 24 ч).
- ONNX Runtime на CPU убирает зависимость от дорогого GPU для инференса.
- K8s HPA позволяет масштабировать сервис инференса под нагрузку.

**Минусы:**
- Операционная сложность Kafka требует DevOps-компетенций.
- Latency end-to-end выше, чем при синхронном REST-подходе (~100–300 мс vs. ~20–50 мс).

### 4.3. Требования к работе системы

| Параметр | Значение |
|---|---|
| Throughput (номинальный) | ≥ 50 RPS (43 200 000 комментариев/сутки) |
| Throughput (пиковый) | ≥ 150 RPS (3× запас) |
| Latency (инференс, p50) | ≤ 80 мс |
| Latency (инференс, p99) | ≤ 300 мс |
| Latency (end-to-end) | ≤ 500 мс от публикации до вынесения решения |
| Uptime | ≥ 99.9 % (< 9 ч простоя в год) |
| Время восстановления (RTO) | ≤ 15 минут |
| Точка восстановления (RPO) | ≤ 5 минут (Kafka offset) |

### 4.4. Безопасность системы

- API инференс-сервиса доступен только через внутреннюю сеть (VPC), не экспонирован публично.
- Kafka: SSL/TLS шифрование трафика + SASL аутентификация.
- Аутентификация в Admin Dashboard: SSO через корпоративный IdP (OAuth2/OIDC).
- Аудит-лог всех действий модераторов с неизменяемой историей.

### 4.5. Безопасность данных

- Персональные данные пользователей (тексты комментариев) хранятся в РФ — выполнение 152-ФЗ.
- Данные для обучения псевдоанонимизируются: user_id хэшируется (SHA-256 + соль), прямые идентификаторы удаляются.
- Срок хранения предсказаний: 180 дней (после — удаление или архивирование в cold storage).
- При наличии EU-пользователей предусмотрен механизм right-to-erasure (GDPR).

### 4.7. Точки интеграции (Integration Points)

- **Comment Ingestion → Kafka:** Kafka Producer API, топик `comments.raw`, формат — JSON `{comment_id, user_id, content_id, text, created_at}`.
- **Kafka → Sentiment Service:** Consumer Group `sentiment-svc`, at-least-once delivery, идемпотентная запись в БД.
- **Sentiment Service → Moderation Service:** топик `comments.scored`, JSON `{comment_id, label, scores, model_version, inferred_at}`.
- **Moderation Service → Social Network API:** REST `POST /comments/{id}/moderate` — скрыть / опубликовать.
- **Admin Dashboard → Moderation Service:** REST API, аутентификация Bearer JWT.

Диаграмма последовательности — [uml_sequence.md](diagrams/uml_sequence.md).

### 4.8. Риски внедрения

| Риск | Вероятность | Митигация |
|---|---|---|
| Дрейф данных — ухудшение модели | Высокая | PSI-мониторинг + ежемесячная доразметка + автооткат к предыдущей версии |
| Эвазионные атаки пользователей | Средняя | Символьный нормализатор + регулярное red-teaming |
| Ложные блокировки → жалобы пользователей | Средняя | Механизм апелляции + снижение порога автоблока до 0.92 |
| Недостаток размеченных данных | Средняя | Краудсорсинг (Толока) + few-shot learning |
| Отказ Kafka | Низкая | Graceful degradation: все комментарии → в ручную очередь; dead-letter-topic |
| Рост трафика × 10 | Средняя | K8s HPA + pre-provisioned capacity plan |
| Претензии регулятора к качеству модерации | Средняя | Аудит-лог + ежеквартальный отчёт о точности системы |
